# Lot 9 — SEO du catalogue

**Ouvert le 16 septembre 2026 sur le commit `c0dea1b` (lot 8).** Ce document porte d’abord l’état avant mesuré, le contrat du lot et ses critères de sortie ; le bilan est ajouté en fin de lot. Tant que la section « Bilan » est absente, rien de ce qui est décrit au futur n’existe.

## État avant, mesuré

- **Un validateur sans appelant.** `apps/api/lib/job-posting-schema.ts` porte la porte d’éligibilité (`markupIneligibility` : candidature spontanée, date de publication absente, titre ou description trop courte, Maison absente, lieu inutilisable, pays non prouvé, conflit libellé/pays, échéance passée, aucune candidature) et le générateur `jobPostingSchema` — hérités de Mode Careers, corrigés le 11/09/2026. **Aucune route de l’API ne les appelle** : seuls leurs témoins et deux commentaires de l’agrégateur les citent, sous leur ancien chemin `apps/web/lib/…`. Le générateur écrit `url` avec `siteUrl()` (repli sur l’URL Railway) et `offerPath` (`/offre/<slug70>-<id>`), une forme d’URL qui n’est pas celle du site (`/emplois/<slug80>-<id>`, `cheminEmploi`).
- **Le site.** `/emplois/[id]` (lot 6C) rend la fiche sans aucune donnée structurée ; `noindex` tant que `EMPLOIS_INDEXABLE=1` n’est pas posé ; une offre fermée ou retirée rend son bandeau avec `noindex` (410 « au cutover, dans `middleware.ts` », non fait) ; un identifiant inconnu rend 404. Les sept sitemaps, `robots.txt`, `jobs.xml` et `llms-full.txt` décrivent le circuit historique `/offres/[slug]` (Neon) ; le nouveau catalogue n’est dans aucun sitemap. `components/seo/JsonLd.tsx` est l’unique point d’injection JSON-LD (sérialisation sans évasion) ; `lib/seo/schema.ts` porte un `jobPostingSchema` propre au circuit historique.
- **Le stock (clone, 16/09/2026).** 82 999 offres publiables ; 81 381 datées ; **80 967** datées, décrites (≥ 100 caractères) et non « candidature spontanée » ; 315 dont l’échéance de la source est passée ; **4 811 sans pays** (aucun `jobLocation` possible : `addressCountry` est requis) ; `countryIntegrity` : `RAW_COUNTRY` 50 446, absent 32 572 ; 55 offres à plusieurs lieux ; **278 offres fusionnées** (`mergedIntoId`), dont l’identifiant historique doit rediriger.
- **Google (documentation officielle, mise à jour du 8 septembre 2026).** Requis : `datePosted`, `description`, `hiringOrganization`, `jobLocation` (avec `addressCountry`), `title` ; `validThrough` requis si l’offre expire ; télétravail : `jobLocationType: TELECOMMUTE` + `applicantLocationRequirements` pour les postes entièrement distants ; `baseSalary` par l’employeur seulement ; le balisage doit correspondre au contenu visible (titre, salaire) ; une seule offre par page. Offre expirée : `validThrough` passé, ou page en 404/410, ou balisage retiré — « failure to take timely action on expired jobs may result in a manual action » ; pour les URL d’offres, Google recommande l’Indexing API plutôt que les sitemaps.

## Contrat du lot

1. **La chaîne branchée, sur le catalogue de l’API.** `GET /api/offres/[id]` rend `balisage: { jobPosting, motifs }` : le `JobPosting` construit par le générateur existant quand la porte l’admet, sinon `null` et les motifs nommés ; `url` et `identifier` pointent la fiche du site. Le chemin canonique d’une fiche (`/emplois/<slug>-<id>`) est calculé par UN algorithme, identique dans l’API (`offerPath`) et le site (`cheminEmploi`), prouvé par témoin sur des titres accentués, ligaturés et longs ; le circuit `/offre/…` de Mode Careers disparaît de l’API.
2. **Le site rend le balisage, et rien d’autre que ce qu’il affiche.** La fiche active injecte le `JobPosting` par `JsonLd` ; une fiche fermée ou retirée n’en porte aucun et reste `noindex` ; un identifiant historique (alias, fusion) redirige de façon permanente vers l’identifiant canonique ; un identifiant inconnu rend 404 ; les métadonnées (titre, description) restent celles du contenu.
3. **Un sitemap paginé du seul stock éligible.** `GET /api/sitemap/emplois?page=n` sert, par pages de 5 000, les chemins des offres publiables, datées, décrites, qui ne sont ni « candidature spontanée » ni échues, avec un `lastmod` vrai (dernière modification de la ligne) ; les offres directes y entrent aux mêmes conditions. Le site sert `/sitemap-emplois-<n>.xml` depuis cette route et n’ajoute la famille à l’index `sitemap.xml` que lorsque `EMPLOIS_INDEXABLE=1` : un sitemap de pages `noindex` serait une contradiction. Aucune combinaison de recherche (marché, filtres, langue) n’entre dans un sitemap.
4. **Canonical et versions réelles.** Le canonical d’une fiche est son chemin nu, quelle que soit la langue d’interface (`/fr/…`, `/en/…` sont des variantes d’habillage : la description reste dans la langue de l’annonce) ; aucun `hreflang` n’est émis pour les fiches. Le module `hreflang` du site reste non branché.
5. **Aucune ouverture d’indexation.** `robots.txt`, `EMPLOIS_INDEXABLE`, l’Indexing API et le 410 des offres fermées restent des cartes de décision ; rien de ce lot n’est déployé.

### Problème corrigé

- **Le validateur a un appelant.** `GET /api/offres/[id]` sert `balisage: { jobPosting, motifs }` (`balisage` de `lib/job-posting-schema.ts`) : le `JobPosting` quand la porte l’admet, sinon `null` et les motifs nommés ; une offre fermée ou retirée n’est jamais balisée (`OFFER_NOT_ACTIVE`), quelle que soit la richesse de son contenu. `directApply` n’est vrai que pour une offre publiée sur Catwalks (le candidat postule ici) ; `url` et `identifier` désignent la fiche du site.
- **Un chemin canonique, un algorithme.** `offerPath` rend `/emplois/<slug>-<id>` (NFKD, 80 caractères, sans tiret final), identique octet pour octet à `cheminEmploi` du site ; deux témoins jumeaux fixent les cas (ligatures, longueur, titre vide). Le circuit `/offre/…` de Mode Careers et le repli vers l’URL Railway (`siteUrl`) disparaissent ; `NEXT_PUBLIC_SITE_URL` fixe l’origine, `https://catwalks.io` par défaut.
- **Le sitemap du seul stock éligible.** `GET /api/sitemap/emplois?page=n` : publiable (deux origines), datée, décrite (≥ 100 caractères), ni candidature spontanée ni échue ; pages de 5 000, ordre stable, `lastmod` = dernière modification réelle de la ligne ; page inexistante → 404, sans clé → 401. Aucune page de recherche, filtre ou marché.
- **Le site rend la chaîne.** La page de l’offre injecte le `JobPosting` reçu (une seule offre par page, sérialisé sans évasion) ; une fiche fermée ou retirée reste lisible, `noindex`, sans balisage ; un identifiant historique (alias, fusion) ou un slug périmé redirige de façon permanente (308) vers le chemin canonique en gardant la recherche ; un inconnu rend 404 ; `/sitemap-emplois.xml?page=n` rend la page de l’API ou 503 ; `sitemap.xml` n’inscrit le catalogue que si `EMPLOIS_INDEXABLE=1`. Canonical d’une fiche : son chemin nu ; aucun `hreflang`.

### Limites

- **Rien n’est indexé** : c’est voulu (passation §16). Le sitemap et le balisage sont prouvés en local ; leur effet sur Google n’est pas mesurable avant l’ouverture.
- **Indexing API** : recommandée par Google pour les URL d’offres (retraits rapides) ; non branchée — elle exige une propriété Search Console et une clé de service, hors périmètre.
- **410 des offres fermées** : la page rend 200 + `noindex` + bandeau, sans balisage (l’un des trois traitements admis par Google) ; le 410 « au cutover » reste une décision.
- **Offres sans pays (4 811 sur le clone)** et pays non prouvés : pas de `JobPosting`, page servie ; elles entrent dans le sitemap si datées et décrites (le sitemap ne juge pas la localisation : la fiche existe et se lit).
- **Multilocalisation** (55 offres) : balisée seulement quand chaque lieu est publiable et le pays prouvé, sinon refusée nommément.
- **`intelligence/*` de l’API** (pages Intelligence de Mode Careers) : code sans appelant hors témoins et `country-ids` ; à traiter au lot 12.
- **`jobs.xml`, `llms-full.txt`, sitemaps `/offres`** : circuit historique, à basculer au cutover (lot 12).

### Cartes de décision

🔷 **DÉCISION — Ouvrir l’indexation du catalogue** · Contexte : la chaîne est prouvée ; `EMPLOIS_INDEXABLE` absent, `robots.txt` et l’index inchangés. Enjeu : deux catalogues indexables avec deux canonicals (`/offres`, `/emplois`) seraient un doublon. Options : A) ouvrir au cutover, avec la bascule des sitemaps historiques et des redirections `/offres/[slug]` → `/emplois/…` (recommandé) ; B) ouvrir avant, en parallèle du circuit historique (doublons) ; C) ne pas ouvrir. Reco : A, avec le lot 12.

🔷 **DÉCISION — Offres fermées : 410 ou page `noindex`** · Contexte : Google admet l’un des trois traitements ; la page fermée conserve aujourd’hui les similaires (seule issue du candidat, audit UX). Options : A) 200 + `noindex` sans balisage (état actuel, recommandé tant que la fiche fermée sert des similaires) ; B) 410 par le middleware (exige un appel au statut par requête) ; C) 410 après un délai. Reco : A, à réévaluer après mesure Search Console.

🔷 **DÉCISION — Indexing API de Google** · Contexte : recommandée pour les URL d’offres, elle accélère indexation et retrait. Prérequis : propriété Search Console, compte de service, quota. Options : A) brancher au cutover, sur les retraits d’abord (recommandé) ; B) sitemaps seuls ; C) ne rien faire. Reco : A, après l’ouverture.

🔷 **DÉCISION — hreflang des fiches** · Contexte : `/fr/` et `/en/` ne traduisent que l’habillage ; la description reste dans la langue de l’annonce. Options : A) un seul canonical par fiche, aucun `hreflang` (appliqué, recommandé) ; B) `hreflang` fr/en (langues fantômes) ; C) `hreflang` seulement quand une traduction du contenu existera. Reco : A puis C.
